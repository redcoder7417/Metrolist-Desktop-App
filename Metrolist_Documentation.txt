# Metrolist Development Documentation

## 1. How the App Works
Metrolist is a full-stack, cross-platform desktop application built using the Electron framework. It functions as a seamless, ad-free music streaming client that interfaces with YouTube Music's backend (InnerTube API) to provide a premium listening experience. 

The architecture is divided into two primary processes:
1. **Frontend (Vite + React)**: The user interface is built with React and rendered inside an Electron Chromium window. It handles all state management (playback, queue, routing, and UI rendering) and communicates with the backend via REST HTTP calls.
2. **Backend (Ktor Kotlin + Java)**: Bundled directly into the Electron app as a standalone `.jar` file, this backend runs locally on port `8091`. It is responsible for making the actual network requests to YouTube Music's InnerTube API, parsing the complex raw JSON responses using `MetrolistExtractor`, bypassing bot protections, and serving clean, structured JSON to the React frontend.

When you search for a song or open the home page, React sends a request to `localhost:8091`. The Kotlin backend fetches the data from YouTube, formats it, and returns it. When you click play, the backend uses `NewPipeExtractor` to decrypt the YouTube video signature and extract the raw `.m4a` audio stream URL, which is then fed into the React HTML5 `<audio>` player.

## 2. Key Components and Functionalities

### Frontend Components
- **`PlayerContext.jsx`**: The heart of the application. It manages the HTML5 `<audio>` element, the current queue, play/pause state, volume, shuffling, and the newly added **Endless Radio** auto-queue feature.
- **`App.jsx`**: The main routing hub. It manages the active tab (Home, Search, Library, Downloads, Settings) and handles global keyboard shortcuts (Space to play, Arrows to skip/seek).
- **`HomeView.jsx`**: Displays dynamic grids and carousels of the user's recommended playlists, charts, and quick picks based on the time of day.
- **`SearchView.jsx`**: Allows the user to query YouTube Music's database for songs, albums, and artists.
- **`Sidebar.jsx` & `RightSidebar.jsx`**: Provides navigation and displays the upcoming queue.
- **`api.js`**: Contains the `fetchWithRetry` logic to ensure the frontend gracefully waits for the Kotlin backend to fully boot up before requesting data.

### Functionalities
- **Endless Auto-Queue (Radio)**: Whenever the queue reaches its last song, the app automatically fetches 15 highly related songs from YouTube's algorithm and appends them to the queue.
- **True Offline Downloads**: Users can click download on any track. The Kotlin backend streams the raw audio and saves it physically to `C:\Users\USER\.metrolist\downloads\`. If the app is launched offline, downloaded songs play instantly from the local hard drive.
- **Local Storage Library**: Liked songs, saved playlists, and user settings are persisted entirely offline using browser `localStorage`.

## 3. Challenges in Development & Solutions

### Challenge 1: Extracting the Audio Stream (Signature Decryption)
**Problem**: YouTube encrypts its audio streams and constantly changes its player JavaScript. Attempting to play a raw YouTube video URL directly in an `<audio>` tag results in a 403 Forbidden error.
**Solution**: We integrated `NewPipeExtractor` into the Kotlin backend. When a song is requested (`/api/stream/{id}`), the backend downloads the YouTube player script, decrypts the signature cipher natively, and returns the direct, unencrypted `.m4a` audio URL to the frontend. 

### Challenge 2: "Up Next" Radio Serialization Crash
**Problem**: When implementing the auto-queue feature, the app crashed with an `HTTP 500` error because the internal `NextResult` InnerTube model wasn't configured to be serialized into JSON. 
**Solution**: Rather than modifying the complex internal InnerTube data structures (which caused compiler errors due to deeply nested missing serializers like `SongItem`, `Album`, etc.), we solved this by mapping the raw InnerTube items into a dedicated, clean `@Serializable` Data Transfer Object (`SearchSong` / `NextResponse`) inside `Application.kt` right before sending the response to the frontend.

### Challenge 3: Backend Startup Race Condition
**Problem**: Because the Electron app spawns both the Vite frontend and the Kotlin backend simultaneously, the React frontend would often load faster than the Java Virtual Machine could boot, resulting in initial "Failed to fetch" connection refused errors.
**Solution**: Implemented an exponential backoff retry mechanism in `api.js` (`fetchWithRetry`). The frontend now intelligently polls the backend and waits patiently for it to become healthy before rendering the Home view, ensuring a smooth startup sequence every time.

### Challenge 4: Seamless Auto-Queue Behavior
**Problem**: The user wanted the queue to auto-fill with related songs, but the logic was initially hardcoded to only run when clicking a standalone track, disrupting playlist playback.
**Solution**: Migrated the auto-queue fetch logic into a `useEffect` hook in `PlayerContext.jsx` that listens to `queueIndex` and `queue.length`. Now, it acts as a true endless radio—dynamically fetching and appending 15 new related tracks only when the user reaches the very end of their current queue, regardless of whether they started from a single song or a playlist.
